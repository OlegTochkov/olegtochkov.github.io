## Что за сайт

Существующий сайт сейчас живёт на платформе **Tilda Publishing** на домене `cleanlogic.by`. Цель проекта — **полностью переписать сайт на собственный код** (стек Astro), чтобы:

1. **Снять юридический риск.** Тильда запрещает использовать экспортированный код вне их платформы.
2. **Получить возможность добавлять сложные фичи**, которые невозможно реализовать в Тильде: личный кабинет, AI-калькулятор по фото, онлайн-чат с менеджером, авторизация по телефону.
3. **Получить актив, который можно продать** другой клининговой компании в будущем — с чистым копирайтом и понятной структурой.

## Юридический контекст миграции

### Что говорит Тильда

Согласно пользовательскому соглашению Tilda Publishing (опубликовано на официальном сайте):

> Нельзя использовать экспортированный программный код для создания страниц вне платформы Тильда. Нельзя вносить изменения в программный код за пределами платформы Тильда. Нельзя тиражировать и распространять экспортированный программный код. Размещать код можно только на домене, который был указан в настройках сайта до экспорта. Нельзя удалять блок с автоматически прикрепляемой ссылкой на принадлежность к основным ресурсам Администрации (за исключением случаев, предусмотренных тарифными планами).

То есть **использовать экспортированный с Тильды код в нашем проекте нельзя**. Нужен полный переписывание с нуля, сохранив только пользовательский интерфейс и собственный контент (тексты, фотографии).

### Что считается "следом Тильды" и удаляется

Любое из этих проявлений запрещено в новом коде:

- Слово `tilda` (в любом регистре) — в именах файлов, классов, переменных, функций, комментариях.
- CSS-классы с префиксами `t-`, `t396__`, `t-rec`, `t-block`, `t-col` (уникальные маркеры Тильды).
- Шрифт **TildaSans** — заменяется на свободный аналог (выбран: **Onest** под лицензией OFL).
- JavaScript-библиотеки из Тильды (`tilda-blocks-*.js`, `tilda-animation-*.js`, `tilda-calc-*.js` и т.п.) — функциональность переписывается с нуля.
- Изображения с хеш-именами от Тильды (например, `tild6637-3533-...png`) — переименовываются в человекочитаемые имена (содержимое самих файлов остаётся).

### Что НЕ считается следом Тильды (можно сохранить)

- Собственные тексты и описания услуг.
- Собственные фотографии — содержимое изображений, не имена файлов.
- Внешние сервисы: Google Tag Manager, Yandex.Metrica, Telegram-боты, виджеты чатов. Это сторонние интеграции, не связанные с Тильдой как платформой.
- Структура SEO (метатеги, sitemap.xml, robots.txt) — это стандартные элементы любого сайта, их формулировки пишутся заново.

### Политика документирования перед удалением

Перед удалением любого Тильда-скрипта или стиля создаётся файл `docs/legacy/<имя-файла>.md` с подробным описанием на русском: что делал, какие функции были, где использовался, какой аналог в новом коде. Только после этого оригинал удаляется. Подробнее: [legacy/README.md](legacy/README.md).

## Перспектива продажи сайта

В горизонте 1–2 лет сайт может быть продан другой клининговой компании. Это означает строгое требование: **в проекте не должно быть никаких объектов с неясным или несвободным копирайтом**.

- Все библиотеки — только под MIT / Apache 2.0 / BSD / ISC / MPL 2.0.
- Шрифты — только под OFL или эквивалентами (Google Fonts подходит).
- Иконки — собственные SVG или из свободных наборов (Lucide, Heroicons, Feather — все MIT).
- Изображения — собственная фотосъёмка или лицензионно чистые источники (CC0 / Unsplash без ограничений).

Эти требования зафиксированы в правиле `.cursor/rules/general.mdc`.

## Кто работает с проектом

Активно с кодом работает **один человек — Максим**. Работа ведётся **только через Cursor** (IDE с интеграцией нейросетей). Остальные четыре человека из команды в код не лезут — они занимаются маркетингом, продажами и операционной деятельностью.

Из этого следует:

- Не нужны командные конвенции (pull request templates, code review workflows, общие style guides для коллег).
- Документация и архитектура заточены под одного оператора.
- Все процессы (включая Git) — локальные, без обязательного GitHub.
- Если в будущем подключится второй разработчик — конвенции дописываются тогда, а не наперёд.
